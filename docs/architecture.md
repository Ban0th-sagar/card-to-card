# CardRoute architecture — Steps 1–4

`frontend/src` separates the HTTP client, auth state and application routes. React Router guards every workspace route; FastAPI independently authorizes every private API call. Desktop sidebar and mobile bottom navigation link to dashboard, cards, pay/route, activity and profile. Cards now supports create, list, details, edit and confirmed removal. Dashboard summary values are computed from the current user’s stored cards. Pay / Route performs read-only structural validation before the simulated quote/eligibility engine. Route Options displays quotes; Activity and Step 5 payment execution remain placeholders.

`backend/app/api`: routes and authorization dependencies. `schemas`: validated Pydantic request/public response contracts. `services`: Argon2id password verification, session issuance and rate limits. `models`: SQLAlchemy entities. `db`: connection/session lifecycle. `core`: environment settings. Alembic owns schema evolution; application startup never calls `create_all`.

## Authentication and access

A signed, eight-hour JWT is held only in a host-only HttpOnly, SameSite=Lax cookie. Production adds Secure; HTTPS is required. Each authenticated request verifies algorithm, signature, expiry, active account and a corresponding non-expired database session. Logout deletes that session, immediately invalidating copied cookies. No bearer token is stored in browser localStorage. Password hashes, JWT secret and database credentials never appear in user API responses. Registration does not start a session; the explicit login step demonstrates authentication.

Cross-origin mutations are rejected, and all mutations require a custom header that HTML forms cannot send. Credentialed CORS permits only the configured frontend origin. Frontend and backend use the same origin through the development proxy or production static hosting. Responses disable caching and sniffing and prevent framing. Validation errors omit submitted values, including passwords. Unexpected errors receive a generic response. API docs are disabled in production.

Normalized email uniqueness is enforced in PostgreSQL. Passwords are 8–128 characters. Users default to CUSTOMER and ACTIVE; database checks constrain role and status. Name-only profile updates reject extra fields, including role. No admin promotion endpoint exists. Argon2id handles password hashing and verification; missing-account login performs dummy verification to reduce timing differences.

Rate limits use atomic PostgreSQL upserts shared across workers: 10 attempts per normalized email and 100 per direct client IP in 15 minutes (registration also consumes attempts). Do not trust client-supplied forwarded headers. Configure a trusted edge limiter and client IP handling when adding a production reverse proxy. Current limits intentionally group requests behind a shared proxy. Rate limits are a basic foundation, not bot protection.

Tables: `users`, `auth_sessions`, `login_attempts`, plus Alembic's version table. `users` has id, email, name, password_hash, status, role, created_at, updated_at and last_login. Timestamps use timezone-aware PostgreSQL columns. Operational maintenance should periodically delete expired sessions and login-attempt rows older than 15 minutes; this step does not add a background scheduler. Use database backups and least-privileged runtime credentials before deployment.

No email delivery, identity verification, password recovery, MFA, full card numbers, PAN/CVV/OTP, payments, route checks or ledger exists. Forgot Password explicitly reports that recovery is unavailable. Deployment remains outside the current scope.


## Step 2 card metadata

`models/card.py`, `schemas/card.py`, `services/cards.py` and `api/cards.py` extend the existing backend; authentication issuance, validation and logout are unchanged. CORS adds DELETE for the new card resource. User/card relationships and the indexed `cards.user_id` foreign key enforce ownership at the model level. Every card query also includes the authenticated user's ID; foreign and missing UUIDs both return 404. Create derives ownership from the session and rejects client user IDs. Delete is a hard delete because there are no transaction dependencies.

Migration `002` adds `cards` after the unchanged `001` foundation. Financial columns use PostgreSQL `NUMERIC(14,2)`. `available_credit` is a stored generated column, so even writes outside the service cannot supply a contradictory available balance. Checks enforce positive credit limit, outstanding in range, valid minimum due, supported networks/statuses, nonblank names and four ASCII digits. Pydantic rejects non-finite values, excessive precision, explicit null patches and unknown fields. PATCH locks the owner-scoped row and validates the merged state before applying changes. Utilization uses Decimal with ROUND_HALF_UP to two decimal places and is returned as a decimal string. No money calculation uses binary floating-point.

Dashboard uses PostgreSQL aggregate sums and weighted portfolio utilization (total outstanding / total limit), with a zero result for empty portfolios. Summary totals include ACTIVE, INACTIVE and BLOCKED cards because status is user-managed metadata. It returns at most four latest card summaries and the nearest due date on or after today in Asia/Kolkata, with deterministic ordering for ties. Overdue cards remain in totals but are not shown as upcoming; a card with zero minimum due may still be the nearest due. No payment instruction is created.

Frontend card screens share `CardForm`, `CardSummary`, `Utilization`, `ConfirmRemove`, a resource-loading hook, and decimal formatting utilities. Money and form previews use BigInt paise arithmetic. Percentage display converts only the already rounded percentage, not money, to a JavaScript number. The API is authoritative. Native dialogs provide focus management and confirmation before deletion. All detail, add and edit screens remain within authenticated routes. Returning to the dashboard refetches server totals. Errors, loading, saving and success states are visible; no financial values are invented on fetch failure.

The optional demo seed creates only a new fixed demo account and refuses existing email addresses. Balances and due dates are self-reported. Utilization categories are UI context and make no credit-score claim. No sensitive credentials, provider, provider eligibility, payment simulation or ledger is present.


## Step 3 read-only structural request validation

`schemas/card_route.py`, `services/card_route.py` and `api/card_route.py` add POST `/api/card-route/validate` without changing authentication or the card-management model/service architecture. No migration, audit table or persisted validation state is added. The request schema permits only UUID source/destination IDs and a finite Decimal amount with at most two fractional places and 14 total digits. Extra authoritative fields are rejected, not used. Malformed requests return 422; non-positive decimal values produce a structural INVALID_AMOUNT result.

A single query loads both IDs restricted to the authenticated user. Missing and foreign IDs return the same generic 404 without either card's metadata, rather than revealing which ID exists. After access succeeds, the ten named checks cover existence, ownership, active statuses, distinct IDs, positive amount, source availability and destination outstanding. Source/destination status failures use SOURCE_INACTIVE / DESTINATION_INACTIVE (messages cover both INACTIVE and BLOCKED). Same IDs produce SOURCE_DESTINATION_SAME. An empty destination balance produces DESTINATION_HAS_NO_OUTSTANDING rather than an over-outstanding error. Checks depending on a positive amount have `passed: null` when the amount is non-positive; these are explicitly not evaluated and do not create unrelated failure reasons. Amount comparisons use Decimal. Failure responses include deterministic reason codes and plain-language messages, while successful responses have all ten checks passed. Snapshots include only safe metadata and the relevant authoritative balance. Cards, balances, timestamps and sessions are not modified by validation.

The frontend adds PayRoute, RouteCardSelector, RouteResult, RouteCTA, RouteOptions and exact-paise quick-amount helpers. Native selects provide keyboard/mobile controls, show non-active cards disabled, and prevent selecting the other role's card. Selected-card panels emphasize source availability and destination outstanding. A request revision counter plus AbortController discards in-flight results after any selection, amount, quick-choice or swap change and during unmount. There is no persisted approval or continuation token. A valid result is shown only for the currently checked form inputs, and the continuation page is a protected static placeholder. Validation does not reserve funds or establish future eligibility; later steps must revalidate current data independently.

Dashboard CTA readiness counts all of the user's cards using GET `/api/cards`, not just the four dashboard previews. It directs users with fewer than two active cards to add/manage cards. Active card tiles can preselect a source via `/route?source=<id>`; only a matching current ACTIVE card is used. Zero/one-active-card states do not show an unusable form. Quick 25%/50% amounts use BigInt paise arithmetic rounded half-up to the nearest paise; API validation remains authoritative. API errors remove any old result; no stale continuation link remains. No fees, provider selection, simulation, payment status, ledger, webhook or financial balance change is implemented.


## Step 4 simulated quotes and eligibility

The existing structural validation service is called first by the new quote service. Structural failures produce no quote; malformed or forbidden data retains safe 422/404 handling. For eligible structural input, the service locks both owner-scoped card rows in stable ID order and reloads structural data before computing a quote. This protects the persisted snapshot against concurrent card edits during creation. Locks are released with the quote/audit commit; no card column is updated or funds reserved.

`CardToCardEligibilityService` keeps rule evaluation separate from API handlers. It checks active cards, distinct IDs, valid amount, source availability, destination outstanding, both simulation route flags, development/simulation mode, fee-inclusive source availability and configured demo limit. Fee arithmetic uses Decimal and ROUND_HALF_UP to paise. Tax is exactly zero. Destination payment is the requested amount; source impact is amount + fee + tax. Settings validate bounded, finite decimal values and a positive expiry duration. Simulation quotes are not offered in production mode.

Migration 003 introduces two default-true simulation flags plus RouteQuote and RouteQuoteAudit. Cards remain otherwise unchanged. Quotes store NUMERIC amounts, original safe display snapshots, fingerprints including updated_at and financial/status/flag fields, configuration snapshots, checks, reasons and timezone-aware expiry. Card references are nullable ON DELETE SET NULL to preserve quote/audit evidence; original internal IDs remain in safe snapshots/audit fields. User foreign keys cascade. No full card number or authentication credential is stored.

Only eligible attempts create ACTIVE quotes. Structurally invalid or demo-ineligible attempts create ROUTE_QUOTE_REJECTED audits without active quotes. Successful creation logs ROUTE_QUOTE_CREATED. Owner-scoped quote GET locks the quote, checks expiry, compares current card fingerprints and configuration, and reruns relevant rules. It transitions once to EXPIRED or INVALIDATED and logs ROUTE_QUOTE_EXPIRED or ROUTE_QUOTE_INVALIDATED. Lifecycle audits are idempotent under repeated reads. Expiration is lazy: expires_at is authoritative even before an expired row is read and transitioned. There is no background scheduler in this step.

The shared revalidate_quote function is the required entry point before any future quote use. Step 5 must additionally perform its own execution-time authorization, card locks and accounting; none is built here. Conservative fingerprints invalidate even nonfinancial card edits. A changed-back card remains invalidated until a fresh quote is requested. No raw quote row should be treated as perpetual authorization.

The frontend starts quote creation only from a successful current Step 3 result. Input changes unmount/cancel that continuation action. The quote page loads persisted quotes before rendering eligibility, uses server_time plus performance.now for the UX countdown, and disables continuation at expiry. Refresh creates a new quote through the same validation chain. Continue to Payment first performs authoritative GET; expired/stale quotes cannot proceed. The destination is a protected static Step 5 placeholder. Ineligible responses retain cost/reason details but create no persisted quote. Browser history state may carry safe analysis data; the backend does not trust it. No real provider connection, payment, ledger, webhook, refund or settlement exists.
